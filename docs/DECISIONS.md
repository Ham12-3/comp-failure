# Decisions log

One entry per decision: what was chosen, and why. Newest phase at the bottom.

## Phase 0: Setup (2026-11-07)

| # | Decision | Why |
|---|----------|-----|
| 0.1 | **`uv` with the `uv_build` backend, `src/` layout, package name `cfp`.** | `src/` layout stops tests accidentally importing from the working tree instead of the installed package. `uv_build` is uv's native backend, so no extra build tool. |
| 0.2 | **Python pinned to 3.12** (`.python-version`, `requires-python = ">=3.12,<3.13"`). | Matches the spec and the Docker base image we will use in Phase 5; one version keeps the lockfile and CI reproducible. |
| 0.3 | **Runtime dependencies added phase by phase**, not all up front. Phase 0 only needs `pydantic` + `pydantic-settings`. | Keeps CI fast and the lockfile honest: every dependency is there because some code uses it. |
| 0.4 | **Config via `pydantic-settings`** (`cfp.config.Settings`), API key held as `SecretStr` and optional. | One place for paths and secrets; the key is masked in reprs/logs (tested). Optional so CI and offline tests run without a key; code that needs it calls `require_api_key()`, which fails with instructions. |
| 0.5 | **ruff** for lint + format (line length 100), rules `E,W,F,I,B,UP,SIM,N,PTH,DTZ,RUF`. | `DTZ` flags naive `datetime` use; date handling is where leakage bugs hide in this project, so we want to be forced to be explicit. `PTH` keeps paths cross-platform (Windows dev, Linux CI). |
| 0.6 | **mypy `--strict`** on `src` and `tests`, with the pydantic plugin. | The spec asks for type hints everywhere; strict mode enforces it rather than hoping. |
| 0.7 | **`network` pytest marker, excluded by default.** | Unit tests must be offline and deterministic. Tests that call the real API run only with `pytest -m network`. |
| 0.8 | **CI on GitHub Actions, `ubuntu-latest`:** `uv sync --locked`, `ruff check`, `ruff format --check`, `mypy`, `pytest --cov`. | `--locked` fails CI if `uv.lock` is out of date with `pyproject.toml`. Single Python version (see 0.2). |
| 0.9 | **All of `data/` gitignored** except the `raw/`, `interim/`, `processed/` placeholders; `mlruns/` and model files gitignored. `reports/` *is* committed. | Data is large and re-downloadable; plots and metrics in `reports/` are evaluation evidence that belongs in the repo. |
| 0.10 | **`.gitattributes` forces LF line endings.** | The dev machine is Windows; avoids CRLF diffs and formatter disagreements with Linux CI. |
| 0.11 | **Dockerfile / docker-compose deferred to Phase 5.** | Nothing to serve yet; writing them now would mean rewriting them later. |

## Phase 1: Data ingestion (2026-11-07)

### Accounts data

| # | Decision | Why |
|---|----------|-----|
| 1.1 | **Sample accounts out of the monthly archives with HTTP range requests instead of downloading whole archives.** Read each zip's central directory (~1.4% of the file), then fetch only the sampled members. | Each monthly archive is 1-4 GB. One per month for 2018-2025 is ~190 GB, far over the 5 GB limit. The archives are on S3, which serves byte ranges, so the whole sample cost 3.57 GB (2.61 GB of zip directories, 0.96 GB of accounts files). |
| 1.2 | **All 94 monthly archives from January 2018 to October 2025.** | October 2025 is the latest filing month whose 12-month outcome window has (just) closed by November 2026. Every month rather than a few, because a company that files late moves to a different month's archive; sampling only some months would under-sample late filers, and late filing is a distress signal. |
| 1.3 | **Company-level sample: keep a company if `sha256("cfp-v1:" + company_number) < 0.5%`.** | The Companies House API (600 requests / 5 min) is the bottleneck in Phase 2, and its cost is per company. Hashing the company number picks the *same* companies in every archive, so each sampled company brings all its yearly filings for the price of one set of API calls. The rule is nested: a higher rate is a superset, so the sample can be grown without redoing work. |
| 1.4 | **Filing date recorded as the archive month (`filing_month`) for now.** | Each archive holds accounts *filed* in that month: the internal run code matches (`Prod224_2510` = Oct 2025) and balance sheet dates cluster about 9 months earlier, the private-company filing deadline. The exact filing date (the spec's prediction date) comes from the filing-history API in Phase 2. Zip member timestamps are the packaging date, not the filing date, so they are not used. |
| 1.5 | **Parse with `ixbrlparse`.** | It reads both iXBRL (`.html`, 99%+) and the older XBRL (`.xml`) files and implements the number transforms, `sign` and `scale`. About 70 ms per file on one core; run in parallel with processes. |
| 1.6 | **The parser extracts values exactly as tagged and derives nothing.** Concept names were picked from tag counts over 700 real 2019 and 2025 filings. Older-taxonomy names (`ShareholderFunds`, `CashBankInHand`, ...) are fallbacks, added only after seeing them in real files. | Keeps parsing auditable against the source file. Ratios, sign repair and imputation belong in Phase 3, where they can be tested on their own. |
| 1.7 | **Keep prior-year comparatives (`*_prev` columns) from the same filing.** | UK accounts restate last year's figures. They were public on the same date as the current figures, so year-on-year change is available from one filing without any leakage risk. |
| 1.8 | **Amounts split by maturity accept both tagging conventions:** `MaturitiesOrExpirationPeriodsDimension` (`WithinOneYear` / `AfterOneYear`) and `FinancialInstrumentCurrentNon-currentDimension` (`CurrentFinancialInstruments` / `Non-currentFinancialInstruments`), alone or together. Creditors tagged with no dimension go to a separate `creditors_no_maturity` column. | The first parser version only knew the first convention and found within-one-year creditors in 35% of filings. Counting dimension combinations on 500 real filings showed the second convention is used more often. Undimensioned creditors (about 3% of filings) are kept apart rather than guessed into a bucket; Phase 3 can derive current liabilities as current assets minus net current assets. |
| 1.9 | **`OriginalRevisedDataDimension` is ignored when matching facts.** | It marks a whole document as original or revised; it does not split a value. Some filing software puts `Original` on every context, which made all values in about 5% of 2023 filings (and 3% of 2024 filings) look dimensioned, so none were extracted. Found by checking filings where no core balance-sheet value was found, which jumped from 0.5% to 5.6% in 2023. |
| 1.9a | **Nested `.zip` members (780 files, 0.003%) are skipped.** | Too rare to be worth the extra code. |

### Companies House API client

| # | Decision | Why |
|---|----------|-----|
| 1.10 | **Token bucket at 1.87 requests/s with a burst of 10.** | A bucket allows at most `burst + rate × window` requests in any window: 10 + 1.87 × 300 = 570, i.e. 5% under the documented 600 per 5 minutes. A test slides a 5-minute window over 1,800 requests to check this. |
| 1.11 | **On 429: empty the bucket, wait `Retry-After` if sent, otherwise 60 s doubling up to 300 s.** 5xx and network errors: back off 2 s doubling up to 120 s, 6 retries. 401/403 fail at once. | The docs say a 429 lasts until the 5-minute window ends, so waiting longer than 300 s never helps. Retrying a rejected key is pointless and would only burn quota. No jitter: there is one client. |
| 1.12 | **Responses cached in one SQLite file, keyed by path + sorted query, storing 200 and 404 with `fetched_at`.** | Nothing is fetched twice, runs can be interrupted and resumed, and a single file is easier on Windows than hundreds of thousands of small JSON files. 404 is cached because it is an answer (e.g. no insolvency history). `fetched_at` records when each snapshot of current state was taken. |
| 1.13 | **Company numbers normalised to 8 characters** (`566433` -> `00566433`). | Sources disagree on leading zeros; the number is the join key across everything. |
| 1.14 | **A blank `COMPANIES_HOUSE_API_KEY=` means "not set".** | Otherwise an empty key gives a confusing 401 instead of a clear "key missing" error. |

### Findings that shape later phases

* **Sign errors in real filings.** Some filers display negative values in brackets but tag them as positive (no `sign="-"`). Example in `tests/fixtures/accounts/Prod224_2510_10851932_20250731.html`: net assets of -7,385 are tagged +7,385. Negative net assets is a key risk feature, so Phase 3 must check and repair signs with accounting identities (e.g. net current assets = current assets - creditors due within one year).
* **Turnover and profit are rarely filed.** Under 5% of small and micro filings include a profit and loss account, so these features will be mostly missing. Missingness itself is a feature (spec section 5).
* **The first API key was for the Test (sandbox) environment.** The live API rejected it with 401, and the sandbox holds none of the real companies we tried (Carillion, Tesco, a sampled micro-entity: all 404). Resolved with a Live-environment key; real responses for every endpoint are saved in `tests/fixtures/ch_api/`.
* **Real responses carry rate-limit headers the docs don't mention:** `X-Ratelimit-Limit: 600`, `X-Ratelimit-Remain`, `X-Ratelimit-Reset` (epoch seconds) and `X-Ratelimit-Window: 5m`. After a 429 the client now waits until `X-Ratelimit-Reset` when there is no `Retry-After`.

## Phase 2: Labels (2026-11-09)

| # | Decision | Why |
|---|----------|-----|
| 2.1 | **Failure = compulsory liquidation, creditors' voluntary liquidation, administration (`in-administration`, `administration-order`) or receivership (`administrative-receiver`, `scottish-administrative-receiver`, `receiver-manager`, `receivership`).** Members' voluntary liquidation is **not** a failure. CVAs, moratoria, restructuring plans and overseas winding up are recorded as "other" and not counted. | Case types come from the official `insolvency_case_type` enumeration. The spec names liquidation, administration and receivership. An MVL needs a sworn declaration that the company can pay its debts in full: it is a solvent wind-down, and counting it would teach the model that profitable owners retiring look like failures. |
| 2.2 | **A case starts on the earliest of its documented start-type dates** (`wound-up-on`, `ordered-to-wind-up-on`, `administration-started-on`, `instrumented-on`, `voluntary-arrangement-started-on`, `moratorium-started-on`, `declaration-solvent-on`), falling back to the earliest practitioner `appointed_on`, then to any date. `petitioned-on` is not a start date. | A winding-up petition can be dismissed, so it is a warning, not a failure. The practitioner fallback matters: Carillion's real record has a practitioner with no `appointed_on`, so neither field can be relied on alone. |
| 2.3 | **Prediction date = the filing-history `date` of the accounts item whose `description_values.made_up_date` equals the balance sheet date**, within the archive's filing month. Fallback: last day of the filing month, flagged in `filing_date_source`. | `description_values` is not in the swagger spec but is present on every real accounts item. The fallback is never earlier than the true filing date, so it cannot leak. In a live trial on 40 companies, all 164 filings matched exactly. |
| 2.4 | **Window = (prediction date, prediction date + 12 months].** Rows where a failure case began on or before the prediction date are excluded (`already_insolvent`). The outcome cutoff is the earliest profile fetch date minus a 30-day reporting lag; rows whose window ends after it are excluded (`outcome_not_observable`). | Spec section 4. The lag allows for the delay between a case starting and Companies House recording it. Excluded rows stay in the table with a reason, so DATA.md can report how many were dropped and why. |
| 2.5 | **Strike-off label = dissolved in the window with no insolvency case of any kind.** | Spec: a separate second target. A company dissolved at the end of a liquidation is not a strike-off. |
| 2.6 | **`company_status` and `date_of_cessation` are dropped from the label output.** | They describe the outcome. Keeping them out of `labels.parquet` means no later step can join them in as features by accident (tested). |
| 2.7 | **Insolvency and charges are fetched only when the profile links to them** (`links.insolvency` / `links.charges`, or the deprecated `has_insolvency_history` / `has_charges`). | Saves a request for most companies. Both forms appear in real profiles, and the swagger marks the booleans deprecated. |
| 2.8 | **One fetch run gets everything Phases 2 and 3 need** (profile, insolvency, full filing history, officers, charges), in sample-hash order. Labels are built from the cache only (`cache_only=True`). | The trial took 3.3 requests per company, so about 98k requests (~14.5 hours) for the full sample. Hash order means a partial run is still a random subsample, and a cache-only build can never trigger a request. |
| 2.9 | **Downloaded the Free Company Data Product** (`BasicCompanyDataAsOneFile-2026-11-01.zip`, 495 MB; 4.06 GB of the 5 GB budget used in total). Used for checks and static attributes only. | One file gives incorporation date, SIC code and postcode for 5.7 million companies. Its status fields describe November 2026, so they are never features. It shows 39% of our sampled companies have been dissolved since and 376 are currently in liquidation, a useful check on the labels. |
| 2.10 | **A case only makes a filing "already insolvent" if it had started and not ended by the prediction date** (end = earliest documented end-type date: `administration-ended-on`, `concluded-winding-up-on`, `case-end-on`...). | Found in real data: companies rescued from administration in 2009-2010 that file normally today. The first version excluded all their later filings. |
| 2.11 | **`--skip-active` fetch mode built but not used:** companies "Active" in the bulk snapshot need no API call for labels. | Checked on 1,548 fetched companies: none had a failure case that could affect a 2018+ label (2 had 2009-2010 administrations that ended). It would cut the label fetch from about 13 hours to 2. Kept for re-runs; not used for this build (2.12). |
| 2.12 | **Build on the companies fetched so far** (2,721 by 9 November 2026) instead of waiting about 13 hours for all 29,584. The fetch keeps running in the background; re-running `build_labels` / `build_features` picks up more. | The API rate limit (600 requests / 5 min) is the bottleneck and was the user's call: move on with the data in hand. Because companies are fetched in sample-hash order, the subsample is random, not biased towards any kind of company. Cost: only 42 failures, so Phase 4 metrics need confidence intervals. |

## Phase 3: Features and leakage tests (2026-11-08)

| # | Decision | Why |
|---|----------|-----|
| 3.1 | **One gate for every API-based feature:** `features/events.as_of` joins events to rows and keeps only those dated on or before the prediction date. Feature modules never join events any other way. | One place to get right and to test, instead of a date filter repeated in every feature. |
| 3.2 | **The leakage test compares each row's features with a register snapshot taken on its prediction date**, on real Carillion data (20 filings, then liquidation, office move to the liquidator, resignations, a later charge) and on a synthetic company covering every event type. Mutation-checked: removing the date filter, or using today's address, makes it fail. | Spec 6 asks for a test that fails if any feature uses later events. Comparing against a snapshot checks the whole feature table at once, including features added later, instead of trusting each feature's own filter. |
| 3.3 | **Filing-history events are dated by their filing `date`; charges by `delivered_on`.** Director appointments/resignations in the last 12 months come from filing history (`AP01`/`AP02`/`288a`, `TM01`/`288b`), not from officer records. | These are the dates the information became public. Officer records and `created_on` carry effective dates, which can be earlier than the public filing. |
| 3.4 | **Registered office postcode reconstructed as of the prediction date** (last move on or before it; else the address the next move left; else today's address only if the company never moved since). Includes `RP05` (Companies House default address applied). | Liquidators usually move the registered office to their own office. Today's address would put insolvency practitioners' postcodes on failed companies: a leak. Checked on real data that address moves, including liquidators', are filed as `AD01`, not on insolvency forms. |
| 3.5 | **Sign repair before any financial feature:** a tagged value is negated only when its negative fits an accounting identity better (net current assets, total assets less current liabilities, net assets, equity), for both years. | Fixes the real "brackets shown, sign not tagged" filings without touching correctly signed ones (tested both ways). Negative net assets is one of the strongest risk signals, so getting its sign right matters. |
| 3.6 | **Year-on-year features use the prior-year comparatives inside the same filing**, not the company's previous filing in our sample. | Always available when the filing has them (77%), never from the future, and no dependency on whether the previous filing happens to be in the sample. |
| 3.7 | **Missingness kept as explicit features** (`missing_*`, `n_numeric_facts`, `has_prior_year`); no imputation in the feature table. | Spec 5: missingness is a signal. LightGBM handles nulls natively; Phase 4 imputes only for logistic regression. |
| 3.8 | **Profile fields allow-listed:** only `date_of_creation`, `type`, `jurisdiction`, `sic_codes`. | Everything else in the profile describes today (status, cessation, due dates, insolvency links). A test checks that the reader ignores them. |
| 3.9 | **Feature registry (`FEATURES`) is the single source of truth:** output columns, docs table and tests all come from it. | Output and documentation cannot drift apart: a test fails if they do. |

### Findings

* **No single feature separates failures with AUC above 0.73** on the first 1,008 companies (22 failures), so there's no sign of leakage. The strongest signals are size and debt (formal insolvency happens to trading companies with creditors; dormant shells get struck off instead), low cash relative to short-term debt, and a history of late accounts.
* **Float rounding noise:** polars can round the last bit of a division differently depending on batch size, so the leakage test compares floats with a 1e-9 relative tolerance.

## Phase 4: Training and evaluation (2026-11-09)

| # | Decision | Why |
|---|----------|-----|
| 4.1 | **Split by filing year: train 2018-2022, validation 2023, test 2024-2025.** | The spec's 2017-21 / 22 / 23 shifted to the years we have. 2024-2025 is the latest period whose 12-month outcome is observable. |
| 4.2 | **Choices are made on rolling validation** (2021, 2022, 2023, each predicted by a model trained on the years before it), never on the test years. | With 9 failures in 2023, one validation year is too noisy to tune on; three years give 20+. Test years are never used for tuning or model choice. |
| 4.3 | **LightGBM stays the main model** although logistic regression scored higher on the test years. | LightGBM is best on rolling validation (PR-AUC 0.028 vs 0.012). Switching after seeing the test set would turn the test set into a second validation set. |
| 4.4 | **Class weighting** (`scale_pos_weight`), then **Platt scaling** on 2023, not isotonic. | Weighting helps the trees see the 0.3% positives; Platt fixes the probability scale afterwards with only two parameters. Isotonic would fit a staircase to 9 failures. |
| 4.5 | **Every test metric has a bootstrap 95% interval.** | 15 test failures: point estimates alone would invite over-reading. |
| 4.6 | **Industry as SIC section (21 levels) instead of 2-digit division (~90); categorical splits smoothed harder** (`cat_smooth=50`, `max_cat_threshold=8`). | The first run's SHAP summary was led by SIC division and postcode area, with validation far above test: memorised categories. These are capacity limits justified by the number of failures, not tuned to the test score. Note: the first run's test numbers were visible when this change was made. |
| 4.7 | **Baselines:** rule = "this filing late (more than 9 months after the balance sheet date) OR negative net assets"; logistic regression on signed-log, median-imputed, scaled numbers plus one-hot categories (rare levels grouped), balanced class weights. | Spec section 7. The rule is the obvious analyst heuristic; the logistic model shows what a linear model gets from the same features. |
| 4.8 | **Explanations: the 5 features with the largest absolute SHAP value, in both directions,** worded from the feature registry ("Current assets / current liabilities: 0.83. This raises the risk."). | Plain English from the same descriptions as the docs. Showing what lowers the risk too is more honest than listing only the alarming parts. |
| 4.9 | **MLflow: full package with a SQLite store** (`sqlite:///mlflow.db`, gitignored). | MLflow 3.18 refuses the old `./mlruns` folder store, and `mlflow-skinny` cannot use a database. |
| 4.10 | **Model files in `models/`** (`lightgbm.txt`, `model_meta.json` with feature order, category levels and calibrator), gitignored. | Phase 5 decides how the API container gets them (train in the image, or commit the small model). |

### Findings

* **The signal is real but weak, and the sample is the bottleneck.** On validation every model beats chance (PR-AUC 0.006-0.028 against a base rate around 0.004), but on 15 test failures the models cannot be told apart. More failures would help more than any modelling change.
* **The API fetch process died at about 18:38 on 9 November** (3,556 companies, no error logged; the machine was at 100% CPU and low memory at the time). The model uses the 3,554 companies fetched by then. The fetch resumes where it stopped if re-run.
* **pandas 3 deprecates building a Categorical from unseen values**, so unseen categories are now mapped to missing explicitly.
